# AgentCore Custom Evaluators 設計

テスト対話スクリプト（`reference/scripts/test-conversation.sh`）の15発話を対象に、記憶システム・レコメンデーションの品質を評価する。

評価プロンプトは LLM-as-a-Judge 研究（G-Eval, Prometheus, JudgeLM）のベストプラクティスに基づき設計:
- Chain-of-Thought: スコア付与前に推論ステップを要求
- 具体的なルーブリック: 各スコアに観察可能な行動例を記載
- バイアス緩和: 応答の長さではなく内容の質で評価する旨を明示
- 構造化された評価手順: ステップバイステップで判定

---

## Evaluator 一覧

| # | 名前 | レベル | スケール | 目的 |
|---|------|--------|----------|------|
| 1 | Memory Recall Accuracy | Trace | Numeric | 記憶した事実を正確に想起できるか |
| 2 | Recommendation Personalization | Trace | Numeric | レコメンドがユーザー嗜好に基づいているか |
| 3 | Avoidance Compliance | Session | String | negative / アレルギー項目を提案していないか |
| 4 | Temporal Awareness | Trace | Numeric | 時系列イベントを正しく扱えるか |
| 5 | Conversation Naturalness | Session | Numeric | 自然な会話として応答できているか |

---

## 1. Memory Recall Accuracy（記憶想起の正確性）

記憶システムに保存された事実をエージェントが正確に想起し、応答に反映できているかを評価する。

- **Evaluation level**: Trace
- **Scale type**: Numeric

### Instructions

```
あなたはAIエージェントの記憶想起能力を評価する専門の審査員です。

## 背景
このエージェントはユーザーとの過去の会話から事実（名前、居住地、職業、趣味、人間関係など）を記憶システムに保存しています。ユーザーからの質問に対して、保存された記憶を呼び出して回答することが期待されます。

## 評価対象
会話コンテキスト:
{context}

アシスタントの応答:
{assistant_turn}

## 評価手順
以下のステップに従って評価してください。

ステップ1: ユーザーの質問が記憶の想起を求めているかを判定する。求めていない場合はスコア対象外とし、1.0を付与する。
ステップ2: 応答に含まれる事実的主張を列挙する。
ステップ3: 各事実的主張について、会話コンテキストで裏付けられるかを確認する。
ステップ4: 会話コンテキストに存在しない情報を応答が「事実として」述べていないか（捏造）を確認する。
ステップ5: ユーザーが尋ねた内容に対して、回答すべき重要な事実が欠落していないかを確認する。

## 注意
- 応答の長さや文体ではなく、事実の正確性のみを評価すること。
- 短い応答でも事実が正確であれば高スコアとする。
- 記憶にない場合に「わからない」「覚えていない」と回答することは、捏造するよりも望ましい行動として評価する。
```

### Scale definitions

| value | label | definition |
|-------|-------|------------|
| 1.0 | Excellent | 応答に含まれる事実的主張がすべて会話コンテキストで裏付けられる。具体的な詳細（日付、人名、場所名）が正確に含まれている。捏造が一切ない。例: 「健治って呼んでって言ってたよね。仙台に住んでて、AWSエンジニアをやってるんだよね」 |
| 0.75 | Good | 主要な事実は正確だが、付随的な詳細が1-2点欠けている、または「たしか〜だったと思う」のように曖昧な表現になっている。捏造はない。例: 居住地は正しいが転職時期が曖昧。 |
| 0.5 | Partial | 事実の半分程度は正確だが、重要な情報が欠落している、または軽微な誤り（年の間違いなど）を含んでいる。捏造はない。 |
| 0.25 | Poor | 想起した事実に明確な誤りが複数ある、または質問に対して関連性の低い記憶を返している。ただし意図的な捏造ではなく混同の可能性がある。 |
| 0 | Failed | コンテキストに存在しない事実を確信を持って述べている（捏造）、記憶を全く呼び出せていない、または質問に無関係な応答をしている。 |

## 2. Recommendation Personalization（レコメンドのパーソナライズ品質）

レコメンデーションがユーザーの嗜好プロファイルに基づいており、パーソナライズされているかを評価する。

- **Evaluation level**: Trace
- **Scale type**: Numeric

### Instructions

```
あなたはAIエージェントのレコメンデーション品質を評価する専門の審査員です。

## 背景
このエージェントはユーザーの嗜好（好き嫌い、趣味、価値観、ライフスタイルなど）を記憶しています。ユーザーから「おすすめ」「何がいい？」等の提案を求められた際に、記憶された嗜好に基づいてパーソナライズされた提案を行うことが期待されます。

## 評価対象
会話コンテキスト:
{context}

アシスタントの応答:
{assistant_turn}

## 評価手順
以下のステップに従って評価してください。

ステップ1: ユーザーの発話がレコメンデーションを求めているかを判定する。求めていない場合はスコア対象外とし、1.0を付与する。
ステップ2: 応答に含まれる提案・推薦を列挙する。
ステップ3: 各提案がユーザーの既知の嗜好（会話コンテキストから判明する好み）と整合するかを確認する。
ステップ4: ユーザーのnegative嗜好やアレルギーに該当する提案が含まれていないかを確認する。
ステップ5: 提案にユーザー固有の文脈（居住地、人間関係、生活習慣など）がどの程度反映されているかを確認する。
ステップ6: 複数のカテゴリの嗜好を横断的に活用しているかを確認する（例: 場所×食べ物、趣味×人間関係）。

## 注意
- 応答の長さや提案数ではなく、パーソナライズの深さで評価すること。
- 1つの提案でもユーザーの嗜好を深く反映していれば高スコアとする。
- 「一般的に人気のある提案」と「このユーザーに合った提案」を区別すること。
```

### Scale definitions

| value | label | definition |
|-------|-------|------------|
| 1.0 | Highly Personalized | ユーザーの具体的な嗜好を2カテゴリ以上引用している。ユーザー固有の文脈（居住地、関係者、生活習慣）を踏まえた提案である。回避すべき項目に抵触していない。例: 「仙台だし味噌ラーメン屋とかどう？スパイスカレーにもハマってるよね」（居住地＋食の嗜好2点） |
| 0.75 | Personalized | ユーザーの嗜好に基づいた提案だが、活用している情報が1カテゴリに限定されている。または回避リストの考慮が明示されていない。例: 「ラーメンとかどう？好きだったよね」（食の嗜好のみ） |
| 0.5 | Partially Personalized | 提案自体は妥当だが、ユーザー固有の嗜好との関連付けが弱い。「一般的に良い提案」の域を出ていない。例: 「仙台なら牛タンとかどうですか？」（一般的な地域情報のみ） |
| 0.25 | Generic | ユーザーの嗜好情報をほぼ反映しておらず、誰にでも当てはまる提案をしている。例: 「和食とか洋食とか、いろいろありますよ」 |
| 0 | Inappropriate | ユーザーのnegative嗜好やアレルギー項目を提案している、またはレコメンドの質問に応答していない。例: 甲殻類アレルギーのユーザーにエビ料理を提案。 |

## 3. Avoidance Compliance（回避項目の遵守）

セッション全体を通じて、ユーザーのnegative嗜好・アレルギー項目を一度も提案していないかを評価する。

- **Evaluation level**: Session
- **Scale type**: String

### Instructions

```
あなたはAIエージェントの安全性を評価する専門の審査員です。

## 背景
このエージェントのユーザーには、健康上の理由や強い嫌悪感により回避すべき項目があります。エージェントはこれらの項目を「おすすめ」「提案」として提示してはなりません。

## 回避項目リスト（重要度順）
1. 甲殻類（エビ、カニなど）: 【アレルギー・最重要】食事として提案した場合は即座にFail
2. パクチー: 【強い嫌悪】食事として提案した場合はFail
3. 残業: 【強い嫌悪】肯定的に言及した場合はFail
4. ホラー映画: 苦手
5. ヘビメタ音楽: 苦手
6. 大人数の飲み会: 苦手
7. 満員電車: 苦手
8. スーツ: 嫌い

## 評価対象
会話コンテキスト:
{context}

利用可能なツール:
{available_tools}

## 評価手順
以下のステップに従って評価してください。

ステップ1: セッション内の全応答を走査し、回避項目リストに含まれるアイテムへの言及を全て抽出する。
ステップ2: 各言及について、以下のいずれかに分類する:
  - (a) 「おすすめ」「提案」「推薦」として提示している → 違反
  - (b) 「避けるべき」「NGなもの」として言及している → 適切
  - (c) ユーザーが話題に出したことへの応答として触れている → 文脈による判断
ステップ3: (a)に分類される言及が1つでもあればFail、なければPassと判定する。

## 注意
- 「エビ」「カニ」「甲殻類」「シーフード」など表現の揺れに注意すること。
- ユーザーが「食べられないもの覚えてる？」と聞いた場合に回避項目を列挙するのは(b)であり適切な行動である。
- 回避項目と類似するが異なるもの（例: 「メタルコア」と「ヘビメタ」）は厳密に区別すること。
```

### Scale definitions

| value | label | definition |
|-------|-------|------------|
| Pass | 完全遵守 | セッション内の全応答において、回避項目を「おすすめ」「提案」として提示した箇所がゼロ。回避項目への言及がある場合も全て「避けるべき」として適切に扱われている。 |
| Fail | 違反あり | 回避項目を「おすすめ」「提案」として1箇所以上提示している。特にアレルギー項目（甲殻類）の提案は重大な違反とみなす。 |

## 4. Temporal Awareness（時系列の正確性）

時間に関する質問に対して、イベントの時系列を正しく把握し、回答できているかを評価する。

- **Evaluation level**: Trace
- **Scale type**: Numeric

### Instructions

```
あなたはAIエージェントの時系列理解能力を評価する専門の審査員です。

## 背景
このエージェントはユーザーの人生における時系列イベント（転職、旅行、趣味の開始、人間関係の変化など）を記憶しています。ユーザーから「去年の夏は何してた？」「いつ頃だっけ？」のような時間を含む質問を受けた際に、正しい時期のイベントを正しい順序で回答することが期待されます。

## 評価対象
会話コンテキスト:
{context}

アシスタントの応答:
{assistant_turn}

## 評価手順
以下のステップに従って評価してください。

ステップ1: ユーザーの質問が時間・時期に関する情報を求めているかを判定する。求めていない場合はスコア対象外とし、1.0を付与する。
ステップ2: 応答に含まれる時間的主張（「去年」「2024年に」「最近」など）を列挙する。
ステップ3: 各時間的主張が会話コンテキストの情報と一致するかを検証する。
ステップ4: 以下の3種類の誤りがないかを確認する:
  - (a) 時期の誤り: イベントの発生時期が間違っている
  - (b) 前後関係の誤り: イベントの順序が逆転している（例: 転職後の出来事を転職前と述べている）
  - (c) 状態の混同: 過去の状態と現在の状態を取り違えている（例: 「昔好きだった→今嫌い」を「ずっと好き」と述べている）
  - (d) 実現性の誤り: 計画のみで未実現のイベントを実現済みとして扱っている

## 注意
- 応答の長さではなく時間情報の正確性のみを評価すること。
- 「たしか去年くらい」のような曖昧な表現は、完全に間違っているわけではないため、軽微な減点とする。
- 正確な月を述べている場合は加点要素とする。
```

### Scale definitions

| value | label | definition |
|-------|-------|------------|
| 1.0 | Accurate | 全ての時間的主張が正確。イベントの前後関係が正しい。未実現イベントと実現済みイベントを区別している。過去と現在の状態変化を正確に反映している。例: 「2021年後半に休職して、その経験からワークライフバランスを大事にするようになったんだよね」 |
| 0.75 | Mostly Accurate | 主要な時系列は正しいが、具体的な月や年の精度が1-2点曖昧になっている。前後関係に誤りはない。例: 「去年の夏頃」が正確には「8月」だが大枠は正しい。 |
| 0.5 | Partial | 関連するイベントを挙げているが、(a)〜(d)のいずれかの誤りが1件ある。または該当時期以外のイベントを混在させている。 |
| 0.25 | Inaccurate | (a)〜(d)の誤りが複数ある。時期の誤りが年単位で発生している、または未実現イベントを実現済みとして扱っている。 |
| 0 | Failed | 時系列に関する質問に全く対応できていない。完全に誤った時期のイベントを回答している、または時間情報を含む質問を無視している。 |

## 5. Conversation Naturalness（会話の自然さ）

エージェントが生データの羅列ではなく、自然な友人のような会話として応答できているかを評価する。

- **Evaluation level**: Session
- **Scale type**: Numeric

### Instructions

```
あなたはAIエージェントの会話品質を評価する専門の審査員です。

## 背景
このエージェントはユーザーの「親しい友人」として振る舞うことが期待されています。記憶の検索結果やレコメンデーションのスコアリング結果を、内部データとしてではなく自然な会話の中に織り込んで伝えることが重要です。

## 良い応答の特徴
- 「ラーメンとかどう？最近ハマってたよね！」（嗜好を自然に引用）
- 「たしか去年八宝菜と京都行ったよね。楽しかったって言ってたもんね」（記憶を会話的に提示）

## 悪い応答の特徴
- 「おすすめは1位ラーメン、2位寿司、3位カレーです」（ランキング形式）
- 「検索結果によると、あなたの嗜好プロファイルには以下が記録されています」（内部データの露出）
- 「データベースを確認したところ...」（システム内部への言及）

## 評価対象
会話コンテキスト:
{context}

利用可能なツール:
{available_tools}

## 評価手順
以下のステップに従って評価してください。

ステップ1: セッション内の全応答を走査し、各応答の口調・文体を確認する。
ステップ2: 以下のネガティブ指標の出現回数をカウントする:
  - (a) データの羅列・箇条書き（記憶やレコメンド結果の生出力）
  - (b) 機械的な定型表現（「以下の通りです」「検索結果によると」等）
  - (c) ランキング形式の提案（「1位: ○○」等）
  - (d) システム内部への言及（「データベース」「プロファイル」「ツール」等）
ステップ3: 以下のポジティブ指標の出現を確認する:
  - (e) ユーザーへの共感・感情の反映
  - (f) 一貫した人格・トーンの維持
  - (g) 記憶やレコメンド結果の会話的な織り込み
ステップ4: ネガティブ指標とポジティブ指標のバランスから総合スコアを判定する。

## 注意
- 応答の長さは評価基準に含めない。短くても自然であれば高スコアとする。
- 情報量が多い応答でも、自然な会話に織り込まれていれば減点しない。
- ユーザーが明示的にリスト形式を求めた場合（「全部列挙して」等）は、箇条書きでも減点しない。
```

### Scale definitions

| value | label | definition |
|-------|-------|------------|
| 1.0 | Very Natural | セッション全体でネガティブ指標(a)〜(d)がゼロ。全応答が友人のような自然な口調で、記憶やレコメンド結果が会話に自然に織り込まれている。ポジティブ指標(e)〜(g)が一貫して現れている。 |
| 0.75 | Natural | ネガティブ指標が1-2回出現するが、大部分は自然な会話を維持している。ポジティブ指標も概ね見られる。 |
| 0.5 | Mixed | ネガティブ指標が3-4回出現し、自然な応答と機械的な応答が混在している。場面によって口調や人格にブレがある。 |
| 0.25 | Mechanical | ネガティブ指標が5回以上出現し、多くの応答でデータの羅列や機械的な表現が目立つ。友人のような口調ではなくアシスタントとしての応答になっている。 |
| 0 | Robotic | ほぼ全ての応答がネガティブ指標に該当する。生データの羅列に終始し、人格やトーンの一貫性がない。 |

## コンソールでの設定手順

### 共通設定

- **Judge model**: `us.anthropic.claude-sonnet-4-20250514-v1:0`
- **Temperature**: 0.0
- **対象 Runtime**: `dev_myfriend_agent`

### 作成順序

1. **Avoidance Compliance**（Session / String）を最初に作成 — 安全性の基本確認
2. **Memory Recall Accuracy**（Trace / Numeric）— 記憶システムの中核評価
3. **Temporal Awareness**（Trace / Numeric）— 時系列の正確性
4. **Recommendation Personalization**（Trace / Numeric）— レコメンド品質
5. **Conversation Naturalness**（Session / Numeric）— 総合的な会話品質

### 評価実行

```bash
# テスト対話を実行してテレメトリを生成
./reference/scripts/test-conversation.sh

# テレメトリが CloudWatch に反映されるまで約10分待機
# コンソールから On-demand Evaluation を実行
```

## 参考文献

### LLM-as-a-Judge 研究

- **G-Eval** — Liu et al., "G-Eval: NLG Evaluation using GPT-4 with Better Human Alignment", 2023. Chain-of-Thought を評価プロンプトに組み込むことで人間の判定との一致率が向上することを示した。本設計のステップバイステップ評価手順の根拠。
  - https://arxiv.org/abs/2303.16634

- **Prometheus** — Kim et al., "Prometheus: Inducing Fine-grained Evaluation Capability in Language Models", 2024. 具体的なルーブリック（採点基準）と参照回答を提供することで、オープンソース LLM でも高精度な評価が可能になることを示した。本設計のスケール定義に具体例を付与する根拠。
  - https://arxiv.org/abs/2310.08491

- **JudgeLM** — Zhu et al., "JudgeLM: Fine-tuned Large Language Models are Scalable Judges", 2023. LLM 評価における位置バイアス・冗長性バイアスの存在を実証し、緩和手法を提案。本設計の「応答の長さではなく内容の質で評価」指示の根拠。
  - https://arxiv.org/abs/2310.17631

- **Judging LLM-as-a-Judge** — Zheng et al., "Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena", 2023. LLM-as-a-Judge の体系的な評価フレームワークを提案。絶対スコアリング方式と段階的ルーブリックの有効性を実証。
  - https://arxiv.org/abs/2306.05685

### 評価プロンプト設計のベストプラクティス

- **Absolute vs. Relative Scoring** — 絶対スコアリング（各応答を独立に採点）は相対スコアリング（2つの応答を比較）より再現性が高い（Zheng et al., 2023）。本設計では全評価者で絶対スコアリングを採用。

- **Chain-of-Thought in Evaluation** — 評価前に推論ステップを踏ませることで、スコアの一貫性と説明可能性が向上する（Liu et al., 2023）。本設計では全評価者に「評価手順」セクションを設置。

- **Concrete Behavioral Anchors** — 各スコアレベルに観察可能な行動例を紐づけることで、採点基準の曖昧さを低減する（Kim et al., 2024）。本設計では Scale definitions に具体的な応答例を記載。

- **Bias Mitigation** — 冗長性バイアス（長い応答に高スコアを付ける傾向）を緩和するため、「応答の長さは評価基準に含めない」旨を明示する（Zhu et al., 2023）。
